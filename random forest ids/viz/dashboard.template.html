How small can a CAN flood detector get?

Three comparators on two features, and the alarm layer above them. The question was how small a per-frame CAN intrusion detector can get, and the answer turned out to be smaller than a random forest — the forests are further down, as the comparison that justifies not shipping one. Every figure here is measured on held-out data: the real HCRL capture, floods built over real attack-free traffic across five injection rates and two victim IDs, an hour at a realistic 1.8 % attack duty, four attacks written specifically to defeat it, and an independent benchmark from a different vehicle.

What ships

Two features, both scale-free: id_rate is this ID's sustained rate where 64 means its normal rate, and dt_ratio_q6 is the current gap in 64ths of its normal gap. A threshold in those units means the same thing on a 10 ms ID, a 1 s ID, and a different vehicle.

The attacks built to defeat it

These were written to break it rather than to be caught. Exact-midpoint phasing is the one to beat: every injected frame sits precisely halfway between two of the victim's real frames, so the arrival pattern stays perfectly regular and the rate never exceeds 2×.

The result

Why alarms, and not per-frame accuracy

Per-frame accuracy is the wrong final metric. The residual per-frame error is the flooded ID's own frames arriving at the flood period, and those are scattered singles. An IDS does not act on one frame: it raises an alarm on an ID. Per ID, a flagged frame adds one to a score that bleeds away with time, and the ID alarms above a threshold.

Two latencies, kept apart. The per-frame verdict is immediate. The alarm takes a few milliseconds because it deliberately waits for corroborating frames, and that wait is what buys the false-alarm rate. A low threshold fires sooner and costs false alarms: at 1 it produces over 19 000 an hour on SynCAN. Eight is the deployed setting, and it is the only one of the three that is clean on every trace here.

The model

These four are the raw per-frame verdict, before the alarm layer. They are the numbers a paper would report, and they are not the ones that matter here: the 8 086 frames flagged in error produce zero false alarms, because every one of them lands on an ID that is genuinely under attack at that moment.

Trained against floods at five injection rates from 2× to 33× a victim ID's normal frame rate, on two different victim IDs, one of which replays that ID's own real payloads so nothing about the payload gives it away. Training on rates rather than on one rate is the whole point, and the section below shows what happens without it.

Training rates

The earlier model was blind to every attack it had not been trained on

An earlier version of this page presented a model trained only on floods running at 33 % duty against a single victim ID, 0x2c0. On its own traces it looked finished. Run unchanged against a second victim ID and against slower floods, it detects none of them — not a degradation, zero. Rate floor

How slow can a flood run before it gets through

Each attack window is labelled with its own injection rate, as a multiple of the victim ID's normal frame rate, then grouped. A flood at 2× adds one frame for every real one; at 33× it is a classic denial of service. Slower attacks are harder, and they are also the ones a real attacker would choose.

Sizing

Past roughly ten comparators, more model buys nothing

Each point is the best forest achievable at that size. A comparator is one feature ≤ threshold test; the count is the total across all trees, which is the thing that actually grows. These are the counts as trained — a frozen model then loses any comparator whose two branches reach the same verdict, so the shipped forest is smaller than its point here.

Generalisation

The model that scores 100 % misses every attack

Trained on the real HCRL DoS capture, it reaches a perfect score on its own test slice. Run unchanged against a flood that reuses a valid ID with plausible payloads, its recall is zero.

Its own thresholds explain it: two of seven trees test pl_popcount ≤ 0, meaning "the payload is all zeros", and another tests dt_ratio_q6 ≤ 0, a value only reachable when an ID has no baseline at all. It learned this ID is not on the whitelist and its payload is blank. It is a whitelist wearing a forest costume.

Read the last row carefully, because it is the clearest case for not judging this by per-frame recall. Frame by frame the deployed model misses 12 % of the real DoS capture's injected frames, which sounds like a material regression against the model trained on that capture. At the alarm layer it catches 73 of 73 of that capture's attack windows, the slowest inside 20 ms. The frames it misses are scattered singles inside windows it has already alarmed on.

The rules

id_rate is a sustained-rate estimate where 64 means the ID is running at its normal rate. dt_ratio_q6 is the current gap as a fraction of that ID's normal gap, where 64 means exactly on schedule. A frame is flagged when a majority of the trees vote attack.

No tree looks at the payload, and none looks at the CAN ID. Every comparator tests either how early a frame arrived for its ID or how much sustained traffic that ID and the bus are carrying. That is deliberate: a model that can see the ID learns a whitelist, and a model that can see the payload learns "the payload is blank", and both are defeated by an attacker who replays a legitimate ID with its own real payloads.

This is a property of the problem, not the model. During a flood the victim's own frames arrive at the flood period like everything else carrying that ID, so they are genuinely ambiguous frame by frame. More trees do not move it, and neither does any payload feature: a purpose-built gated payload tracker reached AUC 0.634 on exactly this discrimination where dt_ratio_q6 already reached 0.929, so it was measured and dropped. What does move it is the alarm layer above: not one of these 2421 frames causes a false alarm, because every one sits inside a window on an ID that genuinely is under attack.

Independent check

A second dataset, different vehicle model, different format

SynCAN (ETAS / Robert Bosch) is an unrelated CAN IDS benchmark. Its test_flooding set is a DoS on an existing ID. It is signal-level rather than raw payload bytes, so only the timing and rate features transfer, and it labels every ID inside an attacked window rather than only the injected frames.
