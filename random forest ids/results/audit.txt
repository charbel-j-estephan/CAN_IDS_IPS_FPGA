That is the number to report for a per-frame IPS, and it is why this design
does not act per frame. Those false positives are overwhelmingly the victim
ID's OWN frames during a flood, which arrive at the flood period and are
genuinely ambiguous one frame at a time. The alarm layer above resolves them:
see the attack-free control below, where every alarm would be false by
construction.

2. GENERALISATION TO CAN IDs HELD OUT OF THE BASELINE
==============================================================================
Does it detect a flood on an ID it has never seen, or has it just memorised
the IDs it was calibrated on? The detector uses no can_id feature at all, so
the question becomes what happens when the per-ID baseline has no entry.

baseline knows 27 IDs; holding out 0x002, 0x131, 0x1f1, 0x2c0, 0x316, 0x370, 0x4b1
this trace's victim IDs: 0x316  (at least one is held out)

baseline complete      recall  99.98 %   FPR 4.6392 %
6 IDs unbaselined      recall 100.00 %   FPR 32.6483 %

on the held-out IDs' own injected frames (59312 of them):
  with a baseline    99.98 % flagged
  without one        100.00 % flagged

An ID with no baseline has recip 0, so its dt_ratio_q6 is 0 on every frame,
which satisfies the timing rule unconditionally. Every frame of an unknown ID
is therefore flagged: 100 % recall on its injected frames and 100 % on its
legitimate ones too, which is the FPR jump above.

That is whitelist behaviour and it is stated rather than buried. On a CAN bus
it is defensible, because the ID set is fixed at design time and an ID nobody
has ever seen is anomalous by existing at all. But it is a property of the
baseline being empty, not of the model detecting anything, and the honest way
to ship it is an explicit known-ID check beside the detector rather than an
accident of a reciprocal being zero. Note also what it means for detection: an
attacker who floods a brand-new ID is caught trivially, which is why the real
HCRL capture's 0x000 flood was never the hard case.

3. WHAT EACH COMPARATOR CONTRIBUTES
==============================================================================
The equivalent of feature_importances_ for a detector that is not a forest:
turn each rule off and measure what is lost.

configuration               recall       FPR   clean-capture FP   worst-trace FPR
---------------------------------------------------------------------------------
both rules (shipped)        99.99%    2.270%                105           12.431%
rate rule only              99.98%    2.214%                  0           12.344%
timing rule only            99.97%    2.133%                105           11.833%

Per-frame recall saturates at 100 % for all three, so it cannot separate them
and is not the axis that matters. False positives are. Read the last two
columns: the timing rule alone is what puts frames on the attack-free capture,
and the rate rule alone is what drives the worst per-trace FPR. Each is
carrying a different failure, which is why both are kept -- not because either
adds recall, because neither does.

==============================================================================
4. SINGLE-FRAME INFERENCE LATENCY (N=1)
==============================================================================
pure-Python, one frame at a time, 20000 frames
  mean 0.35 us per frame   (2,886,289 frames/s)

That number is interpreter overhead, not the design. It is reported because
it was asked for, and it is already 2886x inside a 1 ms budget on a
laptop CPU running Python, which settles the question for any host-side use.

What actually bounds the hardware:
  2 comparators, depth 2, no data dependence between trees
  the tree is depth 2 but the logic is an OR of two independent
    comparisons, so in hardware it is 1 comparator deep plus an OR gate
  the features cost one 16x16 multiply (dt_ratio_q6, by a stored
    reciprocal, no divider) and one multiply-shift-add (id_rate)
  at 500 kbit/s a CAN frame occupies at least 111 bit times, which is 222 us
  so the budget is ~222 us and the work is a handful of cycles

The classifier is 0.02 % of the footprint. Shrinking the forest
from 8 comparators to 3 saved 130 bits; the per-ID table is the design.

Only 27 of the 2048 slots are populated on this bus, so a CAM or a
hash keyed on the observed IDs would cut the table by ~99 %, at the cost of
the direct-index lookup being one cycle.
