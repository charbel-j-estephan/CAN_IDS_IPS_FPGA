How small can a CAN flood detector get?

A random forest that flags injected CAN frames one frame at a time. Trained on one contiguous slice of a capture and tested on a disjoint later slice, never on shuffled rows. Every number below is measured on held-out frames.

HCRL car-hacking · SynCAN flooding · majority-vote scoring

The model

Three trees, eight comparators

Selected on the hardest attack available: a flood that reuses a legitimate CAN ID and replays that ID's own real payloads, so nothing about the payload gives it away.

Sizing

Past roughly ten comparators, more model buys nothing

Each point is the best forest achievable at that size. A comparator is one feature ≤ threshold test; the count is the total across all trees, which is the thing that actually grows. These are the counts as trained — a frozen model then loses any comparator whose two branches reach the same verdict, so the shipped forest is smaller than its point here.

Generalisation

The model that scores 100 % misses every attack

Trained on the real HCRL DoS capture, it reaches a perfect score on its own test slice. Run unchanged against a flood that reuses a valid ID with plausible payloads, its recall is zero.

Its own thresholds explain it: two of seven trees test pl_popcount ≤ 0, meaning "the payload is all zeros", and another tests dt_ratio_q6 ≤ 0, a value only reachable when an ID has no baseline at all. It learned this ID is not on the whitelist and its payload is blank. It is a whitelist wearing a forest costume.

The rules

What the eight comparators actually test

id_rate is a sustained-rate estimate where 64 means the ID is running at its normal rate. dt_ratio_q6 is the current gap as a fraction of that ID's normal gap, where 64 means exactly on schedule. A frame is flagged when 2 of the 3 trees vote attack.

Trees 1 and 2 catch a blank payload arriving far too early. Tree 0 catches a flood on timing and rate alone, without looking at the payload at all. Tree 0 is why the forest still works when the attacker replays valid payloads.

This is a property of the problem, not the model. During a flood, the victim's own frames arrive at the flood period like everything else carrying that ID, so they are genuinely ambiguous frame by frame. More trees do not move it. A verdict at the (ID, time window) level would, which is what a node-exclusion system wants anyway.

Independent check

A second dataset, different vehicle model, different format

SynCAN (ETAS / Robert Bosch) is an unrelated CAN IDS benchmark. Its test_flooding set is a DoS on an existing ID. It is signal-level rather than raw payload bytes, so only the timing and rate features transfer, and it labels every ID inside an attacked window rather than only the injected frames.
